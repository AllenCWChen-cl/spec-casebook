Casebook Analysis Upgrade

How the casebook's spec analysis should change so that it finds the spec agent's cases, the 173 rows added on 10/19 and every later request by itself, and what to leave out before anything is added. Based on the 10/21 comparison: casebook table v1 (291 rows) and spec agent commit 81899f06 (496 iOS cases).

Short answer

Replace the 10/19 bolt-on with passes inside the analysis

Today the analysis reads the spec board by board and writes down what is drawn. The 173 rows from 10/19 came from a one-off script (build_draft.py) run after the analysis, so the next spec update would not produce them again. I propose seven coverage passes inside "Reading the spec" and five standing inputs read on every new or updated draft, with all user requests kept in one ledger. A value check runs before any row is written. Against the 180 spec agent cases the casebook still lacks, these passes would add 44 rows and extend 6 existing ones. They would send 16 cases to PM as questions and leave out 31. The other 44 are already in the casebook.

Proposal 1

Seven coverage passes inside "Reading the spec"

Each pass writes its own section of requirements.md. A cell the spec defines becomes a requirement and gets a row. A cell the spec is silent on becomes an open question, not a row. The exception is the QA rules you set (stop notice, leave and return, waits), which apply to every job.

  1. Flow arrows. List every arrow node on the Design flow boards in board-notes.md, one requirement per arrow. Each arrow needs a row, either its own or an existing row that walks the edge and cites the node in Spec Ref. A forward edge does not cover its return edge. 10/19: 34 rows · gap: 24 trace-only, 0 new
  2. States per job. For each job (outline, cast, chat revision, storyboard and its images, Location, preview, clip, full video, captions, download, notification) fill one grid: start, loading, success, first failure (copy + refund), retry, second failure, partial success, Stop (notice + credits), leave and return, longest wait, completion notice. 10/19: 22 rows · gap: 22 new rows
  3. Fields × rules. List every input (idea, character description, scene image prompt, scene video prompt, rename, age, voice). Apply every rule the spec states for any of them: limit, counter, paste, recover, required, each way to finish editing, discard on close. gap: 7 new rows, 1 extended
  4. Numbers. Every number in the spec (credits, durations, counts, sizes, percentages, line limits) gets a requirement that quotes it. Credit numbers stay binding. gap: 2 new rows
  5. Persistence and sessions. For each thing the app saves (task, title, chat position, thumbnail, episode), check reopen, rename, same session, new session, reinstall and next episode. gap: 7 new rows
  6. MX flows. Tiers, daily chats, charge cards, first-use credits, free trial, discount. The MX file is read as part of the spec set (Design, then MX, then PM). 10/19: 19 rows · gap: 2 new rows from 9 cases
  7. PM-only features. A PM feature with no frame in the newest Design goes to Open questions as "PM-only, ask PM" with its PM frame, and to the update plan's questions. It becomes rows only after PM confirms. It is never skipped silently. gap: 16 cases, 6 questions
Proposal 2

Five standing inputs, read on every new or updated draft

  1. Request ledger library/<feature>/requests.md: every request from you, a colleague or a reviewer, with date, who, the request, its kind (table / run / both), platform and the requirement IDs it produced. The analysis re-applies every "table" entry, and check.ts fails when one has no requirement. Run-only rules (always generate the video, Generate withheld) stay in the skill and the run plan. A one-time import seeds it: the casebook's own dated rules plus the 13 dated requests in the spec agent's source/user-*.yaml. These are your requests, so they belong in the casebook too. 10/19: text 8 + colleague 9 · gap: 3 new rows
  2. Tickets (rule 3, unchanged): open and resolved-not-closed eBugs, all source tags, at the start of each draft. Retire a regression row when its ticket closes. Fold a ticket into a row that already checks it, including rows added in the same draft (TC-211 should have been folded into TC-126). 10/19: 40 rows
  3. Build notes (new): read the RD Note 「驗證重點 (QA)」 on the Testing Request of the build under test. Each point becomes a row in a "Build checks" section that cites the TR. It retires after it passes on two builds, unless the spec also states it. gap: 9 cases added (8 as job states), 7 already-passed points dropped
  4. Template roster (rule 6, unchanged): re-freeze per build, server and locale. Also check the category header icons (your 10/06 request). 10/19: 41 rows
  5. Run findings: an observation (O-n) or a filed bug that no row would have caught gets a row in the next draft. Examples: O-23 price lost after the chat-limit dialog, O-15 no settings card after preview Retry, the cover-title crops. closes the loop
Proposal 3

Value check before any row is written

This runs after the passes and inputs and before draft.csv. Everything it leaves out is listed in the update plan under "Not added", with a reason, so the reviewer can overrule it.

  1. Merge rows that check the same claim: per-tier copies, per-variant copies and a regression ticket that repeats a case.
  2. Drop characterizations that record behavior without a pass/fail expectation, and server behavior a tester cannot see in the app.
  3. Retire one-build checks that already passed, and regression rows whose ticket is closed.
  4. Park, don't drop, rows that need a fixture the run cannot provide (purchase, new account, finite chat limit, microphone). They stay in the table with a needs tag and cost no run time. Money and quota rows are important even when they can't run yet. 22 rows are parked today.

Decisions

What I need from you before changing anything

  1. Apply the analysis changes? Update the skill in both copies (.claude and .codex), add requests.md and extend check.ts (arrows, ledger and job-grid coverage).
  2. Seed the request ledger from the spec agent? This is a one-time copy of your 13 dated requests from its source/user-*.yaml. After that, the casebook stays independent of the spec agent repo.
